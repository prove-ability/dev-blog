# 백엔드·풀스택 프로젝트 기록 가이드

채용 담당자가 문제, 본인 기여, 선택 이유, 검증 근거를 빠르게 확인할 수 있도록 작성합니다. 이 문서는 작성 규칙이며 실제 경험 글이 아닙니다.

## 첫 화면에 담을 요약

- 문제: 대상 사용자, 기존 불편, 제약 조건.
- 본인 역할: 직접 수행한 작업과 의사결정. 팀·AI의 작업은 별도로 구분.
- 설계 선택: 검토한 대안과 선택 이유. 단순 기술 나열은 피하기.
- 검증: 실행한 테스트·재현 조건·관찰한 결과. 수치는 측정 방법과 전후 조건을 함께 기록.
- 한계: 미검증 영역, 현재 남은 문제와 다음 개선.
- AI 활용: 생성·제안된 부분, 본인이 판단·수정·확인한 부분. 설명할 수 없는 구현은 검증 완료로 쓰지 않기.
- 근거: 공개 가능한 코드·PR·테스트 결과·실행 화면 링크. 개인 로그와 토큰은 제거.

## 본문 흐름

1. 배경과 요구사항: 해결하려는 문제와 완료 기준.
2. 구조: 데이터 흐름, 주요 API·모델·권한 경계. 실제 사용한 것만 설명.
3. 핵심 판단: 대안, 실패한 시도와 선택의 근거.
4. 본인 기여: 구체적 변경과 AI/팀과의 역할 구분.
5. 검증과 운영: 해당되는 경우 오류·중복·재시도·동시성·권한·복구를 어떻게 확인했는지.
6. 결과와 한계: 확인된 결과와 다음 과제.

## 필드

기본 title, description, postId, date, status, tags에 다음을 추가합니다.

| 필드 | 값 |
|---|---|
| kind | project |
| featured | 대표 프로젝트일 때만 true |
| evidence.problem | 해결하려는 문제 |
| evidence.ownership | 본인이 직접 수행한 기여 |
| evidence.decisions | 핵심 설계와 대안 |
| evidence.validation | 검증 방법·관찰 결과 |
| evidence.limitations | 남은 한계 |
| evidence.aiUse | AI 활용과 본인 판단의 구분 |
| evidence.links | label, url을 가진 HTTPS 링크 목록 |

아직 자료가 없는 초안에는 evidence를 생략할 수 있습니다. 공개 프로젝트에는 모든 항목이 필요합니다. 초안을 완성하거나 검사를 통과했다는 것만으로 발행이 승인되지는 않습니다.

## 공개 전 확인

실제 작업과 근거를 확인하고 본인이 면접에서 설명할 수 있는 표현으로 수정합니다. 이력서의 이름·경력·학력·연락처는 사용자가 제공하고 공개를 승인한 정보만 사용합니다. 회사 프로젝트를 개인 프로젝트로 표현하지 말고, 공개 허용 범위를 먼저 확인합니다.
